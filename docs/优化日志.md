# MixCut 优化日志

> 从 2026-07-09 起的一轮轮优化记录。**每项改动都编译+重启+截图自测、不改坏已有功能、不自动提交**（攒着供验收）。基线：commit `51c4609`。

## 原则
- 一轮一个聚焦点，改动小、可独立回退。
- 高敏感组件（SegmentInlinePlayer hover 播放 / RangeVideoPlayer / 导出流水线 / 边界微调 / ASR）非必要不动；要动必全量自测。
- 9:16 竖屏、universal、切项目联动、强制浅色 等铁律不破。

## Round 1 · 性能实测（诊断，无代码改动）
- 分镜库静置：**0% CPU**，无 idle 渲染死循环。
- 悬停快速扫过 30 张卡片：瞬时 **36–61% CPU**，停手立即回落 0%。
- 定位：来自库卡片 hover 时的富交互 UI（BoundaryAdjustRow 的多 TextField + `withAnimation` 动画）+ SegmentInlinePlayer 视图切换。**该组件已做多重优化**（轻量缩略图默认态、0.35s hover 防抖、BoundaryAdjustRow 仅 hover 显示）。
- 结论：瞬时尖峰属富 hover UI 的固有成本、非 bug；该组件历史上一改就坏，**不为瞬时尖峰冒险动它**。性能无明显可安全修的 bug。

## 2026-10-19 导出画幅/尺寸唯一真源（千川整批拒收事故）— 台账 `docs/superpowers/plans/2026-10-19-export-canvas-single-source.md`

- **事故**：批量导出的 41 条成片整批被巨量千川以「素材尺寸（宽度）不符合规范」拒收。ffprobe 实测 41 条**全部 480×854**、逐字段一致；截图里 3 条没报错只是因为还没传完（按钮是「取消上传」）。
- **根因（架构层）**：导出侧不存在「画幅/尺寸不变量」这一层，档位→画布的规则被抄成 7 份，且导出前不校验、导出后只回读 start_time/duration、**从不回读宽高**。旧 `.p480 = (480, 854)` 更是结构性不达标——480 宽的精确 9:16 高是 853.33，整数上永远凑不出来。
- **关键反证**：用户同日实传源素材做对照，**480×960 与 704×1248 也被拒**，过的全是精确 9:16 且宽度 ≥720 的标准档 ⇒「宽度下限」「必须精确 9:16」「标准分辨率白名单」三个假设**互相混淆、一个都没被证伪**。**因此本轮没有把任何门槛数字写进代码**，`DeliverySpec` 只登记带日期与一手来源的证据，`judge` 对未覆盖形状一律返回 `.unproven` 且不硬拦。
- **落了什么**：新增 `Sources/MixCutCore/DeliverySpec.swift`（`DeliveryTier` 恰三档、480p 整档删除 ＋ `DeliveryCanvas.size` 唯一换算 ＋ 证据表 ＋ `DeliveryGate`）；6 处尺寸决策改调 Core；导出前闸 ＋ 导出后 ffprobe 回读并与计划值比对（不符即失败并删本次创建的成品）。
